# The coder study: how to run it, and why it cannot be automated

Every refusal rate this project publishes is produced by a lexical rule
(`collectors/generative_firewall.is_refusal` and its party-line counterpart). The hash
chain proves those numbers were never edited after publication. **It cannot prove they
were right in the first place**, and neither can the rule, about itself.

This study is the only thing that can. Two people read the same model responses, without
seeing each other's labels or the machine's, and the agreement between them tells you
whether the construct is even coherent enough to be measured. Then, and only then, the
machine's labels are scored against the rows the two humans agreed on.

Until this is finished, the honest reading of every rate in the repository is **"as
classified by a published lexical rule"**, not "as a human would classify it". That
sentence is currently in `docs/INTEGRITY.md` because it is true.

## Why a model cannot do the coding

The study measures whether a rule agrees with human judgement. A label generated by a
model — including the model that wrote this pipeline — would make the result circular:
it would measure whether one automated judge agrees with another, and then that number
would be cited as evidence that the automated judge matches people. The project's own
method statement forbids routing judgement through a model anywhere in this path, and
`validation/CODEBOOK.md` requires coders to be blind to machine labels.

So the labelling step is the one part of this repository that a person has to do. Two
people, about 35 minutes each.

## Running it

**1. Draw the sample** (already done; re-draw only if you intend a new study).

```bash
OPENROUTER_API_KEY=... python3 scripts/gfi_validation_sample.py
```

Writes `validation/out/` (git-ignored): two identical blind sheets, an answer key the
coders must not open, and a manifest recording the strata pools, the draw counts and the
Horvitz-Thompson weights that turn a sample rate into a population rate.

**2. Pre-register, before anybody codes.**

```bash
python3 scripts/validation_preregister.py
```

Seals the sample digest, the codebook digest, the design weights, the analysis plan and
the acceptance thresholds into `readings/eval-registry.jsonl`, and writes
`validation/PROTOCOL.json`. It refuses to run if the sheet already carries labels,
because a study pre-registered after coding is not pre-registered.

This is the step that makes the eventual number credible regardless of who coded it. A
coder study that can be quietly re-drawn after a disappointing alpha is worth exactly
what a model eval that can be quietly re-run is worth, and this project's whole argument
is that the second one is worth nothing.

**3. Two people code, independently.**

Open `validation/code.html` in a browser (a `file://` URL is fine; it makes no network
requests). Enter your initials, drop in your sheet — `coding_sheet.csv` for coder 1,
`coding_sheet_2.csv` for coder 2 — and label with keys `1` / `2` / `3`. Progress is saved
in your own browser, so you can stop and resume, and the two coders cannot see each other
even on one machine. Export when done and save over your sheet.

Read `CODEBOOK.md` first. The three labels apply in a fixed order and the
`refused` / `party_line` boundary is the whole difficulty: `refused` is for declining to
engage, never for engaging badly. Looking up what actually happened in an event is
expected. Working out which model produced a response is not. Do not open
`answer_key.jsonl`. Do not compare notes until you have both exported.

**4. Report.**

```bash
python3 scripts/gfi_validation_agreement.py \
  --coder1 validation/out/coding_sheet.csv \
  --coder2 validation/out/coding_sheet_2.csv \
  --key validation/out/answer_key.jsonl \
  --manifest validation/out/manifest.json \
  --require-preregistration \
  --report validation/out/agreement_report.json
```

`--require-preregistration` refuses to report against a sheet whose digest is not the one
frozen in the chain. Use it. Without it the study is just two spreadsheets.

## How to read the result

**Krippendorff's alpha is the headline**, with its bootstrap interval, and its band is
not negotiable after the fact because it was frozen in step 2:

| alpha | band | what it means |
|---|---|---|
| ≥ 0.800 | rely | the labels support a published machine-agreement figure |
| 0.667 – 0.800 | tentative | caveated conclusions only; sharpen the codebook first |
| < 0.667 | reject | the construct is too fuzzy for people to apply; no machine score against it means anything |

Cohen's kappa is printed alongside for familiarity. Where the two disagree, believe
alpha: kappa builds chance agreement from each coder's separate marginals, which inflates
it when one label dominates, and this draw is dominated by `answered` — 489 in the pool
against 17 `refused`.

**A low alpha is a result, not a failure to be re-run.** It would mean the
refusal/party-line distinction cannot be applied consistently by careful people, which is
a finding about the construct and worth publishing as one. The pre-registration exists so
that outcome cannot be quietly replaced with a friendlier second attempt.

**Two numbers, never one, for the machine scores.** Raw sample counts describe the coded
rows. The Horvitz-Thompson figures describe the population of responses, and they are the
ones to quote — the draw deliberately takes rare strata near-exhaustively and thins the
huge `answered` pool, so an unweighted recall reads high by a wide margin.

## Known limits of the sample as drawn

- **`refused` is thin.** The pool held 17 against a target of 60, so recall on the one
  label the frontier suite depends on will carry a wide interval. That is disclosed in the
  manifest and sealed in the pre-registration rather than papered over. Raising it needs a
  larger collection, not a different draw from the same one.
- **`party_line` fell short too**, 38 against 50, for the same reason: undisguised
  state-narrative answers are genuinely rare in what these models produce.
- **The sheets are git-ignored.** The pre-registration therefore proves the sample was
  fixed before coding, but a third party cannot yet check the rows against it. Publishing
  the blind sheet after the study completes would close that, and costs nothing: it
  carries no machine labels.
- **This study validates the GFI three-label classifier.** The frontier over-refusal
  suite uses the same `is_refusal` on different material, so it inherits the `refused`
  result but not the `party_line` one. `readings/refusal-drift-transcripts.json` now
  publishes raw frontier responses, which makes a matching frontier draw possible for the
  first time.

## Files

- `CODEBOOK.md` — the coding manual. The instrument; its digest is sealed at step 2.
- `README.md` — this file.
- `PROTOCOL.json` — written by step 2: what was frozen, and the bar it will be read against.
- `code.html` — the blind coding interface.
- `out/` — git-ignored working files: the sheets, the answer key, the manifest, the report.
- `core/agreement.py` — alpha, kappa, the bootstrap, the bands. Tested against hand
  arithmetic in `tests/test_agreement.py`.
